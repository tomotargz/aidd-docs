$1 の振り返りを行います。

## 対象範囲

振り返るのは**開発プロセス**であり、教材の内容ではありません。内容の改善は `/review-doc` の役割です。
改善の反映先は次の4つに限定します。それ以外を変えたくなった場合、プロセスの問題ではない可能性を疑ってください。

`foundation/style-guide.md` / `foundation/review-criteria.md` / `.claude/agents/*` / `.claude/commands/*`

## 手順

### 1. 事実を収集する（推測を混ぜない）

| 収集するもの | 方法 |
|---|---|
| 指摘の傾向 | `logs/review-log.md` から該当章の行を抽出し、カテゴリ別・重大度別に集計する |
| 頻出する指摘の類型 | 同じ類型が2件以上のものを列挙する（3件未満で発火していないものも含む） |
| PR の数と手戻り | `git log --oneline` でブランチ・コミット履歴を確認する。`outline/` の後に構成を変えた `draft/` がある場合は手戻りとして数える |
| 所要期間 | 最初のコミットから章完了までの日数 |
| アウトラインからの乖離 | `outline.md` の各節の主張と、完成した原稿の主張を比較する |
| バックログの消化 | `backlog.md` の該当章のタスクのうち、途中で追加されたタスクを数える |

### 2. 人の体感を聞く

事実を提示したうえで、**必ず次を質問し、回答を得てから分析に進んでください**。

- どこがしんどかったか
- AIの出力のどこに不満があったか
- 時間を無駄にしたと感じた作業は何か

### 3. 分析する

- 数字が多い項目に飛びつかない。**なぜその指摘が多かったのか、原因の仮説を立てる**
- 手戻りが起きた PR は、どのフェーズの判断が原因だったかを特定する
- 「うまくいった」と感じたことも、事実（指摘の少なさ、手戻りのなさ）と結びつける

### 4. `retrospectives/$1.md` を書く

`retrospectives/README.md` のテンプレートに従います。構成は 事実 / Keep / Problem / Try。

- **事実** — 集計結果。解釈を混ぜない
- **Keep** — 続けること。必ず事実に紐づける。「うまくいった気がする」は書かない
- **Problem** — 問題と原因の仮説をセットで書く
- **Try** — 次の章で試す具体的な変更。**反映先のファイル名を必ず含める**

### 5. Try をバックログに積む

`backlog.md` の「プロセス改善」に転記します。1行1タスク、反映先のファイル名と、この振り返り（`ret-$1`）への参照を含めます。

### 6. 完了処理

- `backlog.md` の該当章のタスクをすべて完了にする
- `sources/references.md` の「再確認が必要な出典」を確認し、該当章のツール依存の出典に次回確認予定を設定する
- ブランチ `retro/$1` でコミットする

**このコマンドでは改善を適用しません。** 適用は別 PR（`process/` ブランチ）で行います。診断と変更を分けることで、「なぜこのルールがあるのか」が git 履歴から辿れます。
