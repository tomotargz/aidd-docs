$1 に含まれるデモ手順を検証します。

## このコマンドが必要な理由

教材は研修後に受講者が一人で読み、デモで見た操作を自分で再現する（`foundation/audience.md`「教材の使われ方」）。
**動かない手順は、自習中の受講者を確実に止める。** レビュアーは文章として読むだけなので、手順が実際に動くかは検証しないと分からない。

## 実行するかの判定

原稿に次のいずれかが含まれる場合のみ検証します。含まれない場合は「検証対象なし」と報告して終了します。

- 受講者が実行することを想定したコマンド
- ファイルの作成・編集手順
- ツールの設定手順
- 画面表示・出力例の提示

## 手順

### 1. 検証環境を用意する

- 作業はスクラッチディレクトリで行う。**教材リポジトリを汚さない。**
- `foundation/audience.md` の前提知識を確認し、**受講者が持っていない前提に依存していないか**を見る。前提外のツールが必要なら、それ自体が指摘になる。

### 2. 手順を抽出する

原稿から、受講者が実行する操作を順番に列挙します。列挙した時点で次を確認します。

- 前の手順の結果に依存しているのに、その依存が書かれていない箇所はないか
- 環境（OS、シェル、ツールのバージョン）への依存が明示されているか

### 3. 実際に実行する

**書かれているとおりに、書かれている順番で実行します。** 行間を自分の知識で補完してはいけません。補完が必要になった時点で、それは手順の不備です。

各手順について記録します。

| 記録項目 | 内容 |
|---|---|
| 実行したコマンド | 原稿の記述をそのまま |
| 結果 | 成功 / 失敗 |
| 出力の一致 | 原稿に出力例がある場合、実際の出力と一致するか |
| 補完の要否 | 原稿にない知識・操作が必要だったか |

### 4. 指摘を出す

`foundation/review-criteria.md` の「指摘の書式」に従います。カテゴリは `fact`、重大度は次の基準で判断します。

| 重大度 | 条件 |
|---|---|
| `Critical` | 手順が失敗する。書かれたとおりでは再現できない |
| `High` | 実行はできるが、原稿にない知識の補完が必要だった |
| `Medium` | 出力例が実際と異なる。環境依存が明示されていない |

指摘は `logs/review-log.md` に**カテゴリ `fact` で記録します**（検証専用のカテゴリは作りません。固定語彙を増やすと集計が崩れるため）。
指摘要約には「デモ手順が再現できない」のように、検証由来であることが分かる類型を使います。

### 5. 検証結果を frontmatter に記録する

検証を通過したら、原稿の frontmatter に次を追記します。

```yaml
demo_verified: 2026-08-22          # 検証日
demo_environment:                   # 検証した環境
  os: macOS 15
  claude_code: "2.0"
```

**検証日は実際に実行した日を書きます。** 環境が変われば再検証が必要になるため、この記録が再検証の判断材料になります。

### 6. 次のアクション

- 検証で見つかった不備は、このコマンドでは直しません。`fix/` ブランチで反映します
- 検証を通過したら `/review-doc $1` に進みます

**手順を実行できなかった場合（必要なツールがない、環境が用意できない等）は、検証したふりをせず、その事実を報告してください。** 未検証の手順を検証済みとして記録することは、この工程を無意味にします。
