# レビュー観点

**この文書に書くのは「どう評価するか」だけである。** 評価の基準となる中身は `audience.md` / `curriculum.md` / `style-guide.md` / `glossary.md` にある。

`/review-doc` が起動する5つのサブエージェントの判定基準を定義する。
カテゴリと重大度の語彙は固定する。集計可能であることが、振り返り（`/retro`）の前提になるため。

---

## カテゴリ（固定語彙）

`review-log.md` に記録する際は、必ずこの6語のいずれかを使う。

| カテゴリ | 担当エージェント | 見るもの |
|---|---|---|
| `fact` | fact-checker | 事実の正確性、出典の有無、情報の鮮度 |
| `logic` | logic-reviewer | 主張と根拠のつながり、論理の飛躍、章間の整合 |
| `paragraph` | writing-reviewer | 段落構造（1段落1トピック、要約文の位置） |
| `tech-writing` | writing-reviewer | 文の明晰性（一文一義、係り受け、曖昧語） |
| `style` | style-reviewer | 表記・用語・文体の統一 |
| `audience` | learner-reviewer | 受講者が前提知識だけで読めるか |

## 重大度（固定語彙）

| 重大度 | 定義 | 例 |
|---|---|---|
| `Critical` | 受講者に誤った情報が伝わる／受講者が確実に手を止める | 出典のないツール仕様の断定、事実誤認、未定義用語での説明 |
| `High` | 主張が伝わらない、または根拠が欠けている | 論理の飛躍、段落に複数トピック、到達目標と内容の不一致 |
| `Medium` | 読みにくさとして蓄積する問題 | 一文が長い、曖昧語、表記ゆれ |
| `Low` | 好みの範囲、改善するとより良くなる程度 | 語順、言い換えの提案 |

**マージ条件（Definition of Done）**

1. `Critical` と `High` が0件であること。
2. デモ手順を含むファイルは、`/verify-demo` の検証を通過していること（frontmatter に `demo_verified` があること）。

## 手順検証（/verify-demo）

デモ手順を含む原稿は、`/review-doc` の**前**に `/verify-demo` で実際に実行して確認する。
レビュアーは文章として読むだけなので、手順が動くかは検証しないと分からない。

- 検証で見つかった不備は、カテゴリ `fact` として `logs/review-log.md` に記録する。検証専用のカテゴリは作らない（固定語彙を増やすと集計が崩れるため）。
- 指摘要約には「デモ手順が再現できない」のように、検証由来と分かる類型を使う。
- 検証を実行できなかった場合は、検証済みとして記録しない。

## 指摘の書式

すべてのエージェントは、指摘を次の形式で返す。この形式でないと `/review-doc` が集計できない。

```markdown
### [重大度] カテゴリ | 一行の見出し
- **箇所**: ファイルパス:行番号（または該当箇所の引用）
- **問題**: 何が問題か。1〜2文
- **根拠**: どのルール・どの一次情報に照らして問題か
- **修正案**: 具体的な代替案。書き換え文を示せる場合は示す
```

指摘は**重大度の高い順**に並べる。

## エージェント共通の制約

1. **推測で指摘しない**。ルールまたは一次情報を根拠として示せない指摘は出さない。
2. **原稿を編集しない**。レビューは読むだけ。修正は `fix/` ブランチで別途行う。
3. **良かった点を1〜2個は挙げる**。振り返りで「維持すべき運用」を判断する材料になる。
4. **重大度を水増ししない**。すべてが Critical なら、優先順位が失われる。

## 3回ルール

同一カテゴリで**同種の指摘が3回以上**記録されたら、個別に直すのをやめ、仕組みで防ぐ。

- 検出: `/review-doc` の実行末尾で `logs/review-log.md` を集計する
- 対応: `backlog.md` の「プロセス改善」に、ルール化タスクを1行追加する
- 反映先: `style-guide.md` / `review-criteria.md` / `.claude/agents/*` / `.claude/commands/*` のいずれか
- その場では原稿を直すだけにとどめ、仕組みの変更は別 PR（`process/` ブランチ）で行う

「同種」の判定は、指摘要約の類型が一致するかで見る（例: 「1段落に複数トピック」は語尾が違っても同種）。
