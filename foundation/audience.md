# 受講者像

この文書は**受講者**を定義する。すべての執筆とレビューはここを基準に判断する。
`learner-reviewer` はこの文書の人物になりきって原稿を読む。

> [!IMPORTANT]
> この文書に書くのは「誰が、どんな状態で読むか」だけである。
> 何を教えるか（学習目標・章立て・扱う範囲）は `curriculum.md`、どう書くかは `style-guide.md` に書く。

## 受講者が教材を読む状況

受講者は2日間の集合研修に参加し、その後も同じ内容に触れる。ただし**触れる形が場面によって異なる**。

| 場面 | 受講者が見るもの | 受講者の状況 |
|---|---|---|
| 研修中 | この教材から作成したスライド | 講師の講義を聞きながらスライドを目で追う。自分で手を動かすことはなく、操作は講師のデモを見る。分からなければその場で質問できる |
| 研修後の自習 | この教材そのもの | 一人で読み、デモで見た操作を自分で再現する。質問できる相手がいない |

**この教材の直接の読者は、研修後に一人で読む受講者である。** 研修中はスライドが介在するため、`learner-reviewer` は常に「質問できる相手がいない状態で読む人」として原稿を読む。

研修そのものの設計（形態、日数、進め方、規模）は `curriculum.md` に書く。ここに書くのは受講者が置かれる状況だけである。
執筆時に守るべき制約は `style-guide.md`「6.1 デモ手順の書き方」を参照。

## 前提知識

「前提」が「あり」のものは、受講者がすでにできると仮定してよい。
「なし」のものは、受講者が知らない。

| 領域 | 前提 | 備考 |
|---|---|---|
| プログラミング実務経験 | あり | 実務経験3年以上のエンジニアが中心 |
| Git / GitHub | あり | ブランチを切り、PR を出してレビューを受ける流れは身についている |
| ターミナル（CLI）での作業 | あり | コマンドライン操作に抵抗がない |
| チャット型の生成AI | あり | ChatGPT 等を日常的に使っている |
| コーディングエージェント | **なし** | Claude Code を含め未経験。エージェントとチャットの違いから説明が必要 |
| ユニットテストの作成 | **なし** | 書く習慣があるとは仮定しない |
| CI/CD パイプライン | **なし** | 構築・運用の経験があるとは仮定しない |

## 受講者が抱えている課題

課題は受講の**前**と**後**に分かれる。

### 受講前に自覚している課題

1. **エージェントを使った開発のイメージが湧いていない。** 未経験のため、何がどう変わるのかを具体的に思い描けない。
2. **使ってみたが、期待するアウトプットが得られない。** 指示の仕方が分からず、見当違いのコードが返ってくる。結局自分で書き直している。
3. **使いどころの判断がつかない。** どこまで任せてよく、どこから自分でやるべきかの境界が分からない。
4. **生成されたコードの品質を保てるか不安。** レビューで確認しきれない、テストや設計の一貫性が崩れる、といった懸念がある。

### 受講後に直面する課題

受講中には実感がないが、実務で使い始めてから顕在化する。

5. **エージェントを使い始めた開発者が一般に遭遇する問題。**
6. **慣れてきた後、開発生産性が思ったほど向上しない。** 操作に習熟しても成果が伸びない段階で行き詰まる。

課題5と6は、受講時点では自分の課題として認識されていない。**教材は「今は分からなくても、後で戻ってくる場所」として読まれる。**

## 受講者の期待

**受講者は自分の意思で申し込む。** 会社の指示で座っているのではないため、期待は具体的で切実である。「何となく聞きに来た」受講者を想定しない。

### 期待していること

1. **自分の開発が速くなること。** 手段は問わない。結果として自分のアウトプットが増えることを求めている
2. **判断基準を持ち帰ること。** どこまで任せてよいか、何を気にすべきかを、自分で判断できるようになりたい
3. **明日から使える具体的な手順・設定。** そのまま真似できるものを持ち帰りたい

### 期待しているが、この研修では提供しないもの

1. **「使い方を学べばすぐ速くなる」という即効性**
2. 特定の言語・フレームワークでの実装ノウハウ

> [!WARNING]
> 1は教材の中心的な主張と正面から衝突する。受講者は「AIの使い方」を学びに来るが、
> 教材は「テスト自動化や CI/CD がなければ速くならない」と主張する。
> このギャップの扱いは、受講者の満足度を最も左右する。
> どう扱うか（早期に明示するか、体験を経て納得させるか）は `curriculum.md` で設計する。

「組織導入の進め方、上司を説得する材料」は**提供する側**である。受講者一人では変えられない部分について、必要性を説明できる水準を目指す。

## 受講後の姿

受講後に到達させたい状態は**学習目標**であり、`curriculum.md` に置く。この文書では扱わない。

`learner-reviewer` は、原稿を評価する前に `curriculum.md` の学習目標も読むこと。何ができるようになるべきかを知らずに読むと、到達目標との過不足を判断できない。

## 想定しない読者

宛先を絞ることで、教材の焦点がぼやけるのを防ぐ。

- **導入の可否を判断する立場の人。** 費用対効果や製品比較を求める意思決定者は対象としない。受講者は現場のエンジニアである。
- **エンジニア以外の職種。** PM・QA・デザイナーは対象としない。コードを書くことを前提とした記述をしてよい。
