# カリキュラム

この文書は教材全体の設計図である。`backlog.md` の章立ては、この文書から機械的に展開する。

誰に向けて書くかは `audience.md`、どう書くかは `style-guide.md` に書く。この文書に書くのは**何を教えるか**である。

## この文書の構成

| 部 | 内容 | 読むとき |
|---|---|---|
| 第1部 決定 | 何を、どの順で教えるか | 執筆とレビューのたび |
| 第2部 判断の記録 | なぜそう決めたか | 決定を変えたくなったとき |

**執筆と `/review-doc` は第1部だけを根拠にする。** 第2部は同じ検討を繰り返さないための記録であり、教材の判定基準ではない。

決定を変えるときは、第1部を書き換え、変えた理由を第2部に足す。

# 第1部 決定

## 研修の制約

学習目標と章立ての分量は、この制約から決まる。

| 項目 | 内容 |
|---|---|
| 提供形態 | 社外向け研修（有償） |
| 受講形態 | 2日間の集合研修 |
| 進め方 | 講義中心。手を動かすのは講師によるデモのみ |
| 想定人数 | 未確定（講義中心のため章構成への影響は小さい） |

## 教材の方針

- **原則中心、事例として Claude Code**。考え方・進め方を軸に置き、ツールは具体例として登場させる。
- ツール固有の記述は、原則の記述と混ぜず、囲み（`> [!NOTE]`）で分離する。詳細は `style-guide.md` を参照。
- **位置づけ**: 「AIを速く使う技術」ではなく「**AIが効く状態を作るエンジニアリング**」を教える。

### 中心的な主張

> 開発生産性を上げるには、エージェントにコーディングをさせるだけでは不十分である。

この主張は DORA の 2025 年の研究知見に支えられている。

> "AI acts as an amplifier, but the greatest returns come from focusing on the underlying sociotechnical systems."
> — [DORA Research](https://dora.dev/research/?view=detail)（2026-08-26 確認）

AI は既存のシステムを増幅する。制約がコーディング速度以外の場所にあるなら、コーディングを速くしても全体は変わらない。教材はこの一点を軸に構成する。

## 学習目標の水準

各目標には水準を付す。定義は次のとおり。

| 水準 | 定義 |
|---|---|
| **実践できる** | 教材を手元に置いて、自分の実務で実行できる |
| **説明できる** | 必要性とその根拠を、自分の言葉で他者に述べられる |

**「実践できる」は研修中にできることを指さない。** 到達点は教材を見ながら実務で実行できることである（理由は第2部）。

## 全体の学習目標

受講者の課題（`audience.md`）への応答として設計する。対応する DORA capability があれば注記する。

**目標に capability が対応している必要はない。** 必要なのは根拠であって capability ではない。O1 と O2 は capability を持たないが、それぞれツールの公式ドキュメントと DORA の研究知見に支えられている。

番号は学習の順序を表す。

出典: [DORA Capabilities](https://dora.dev/capabilities/)（2026-08-26 確認）

### O1. エージェントを使った開発がどのように進むかを、自分の手元で再現できる【実践できる】

- **応答する課題**: 1（エージェントを使った開発のイメージが湧いていない）
- **対応する capability**: なし（DORA の射程外。出典はツールの公式ドキュメント）
- **位置づけ**: 前提知識「コーディングエージェント: なし」を埋める。教材の要件2に対応する

### O2. AIにコードを書かせるだけでは生産性が上がらないことを、根拠を挙げて説明できる【説明できる】

- **応答する課題**: 5・6（使い始めてから遭遇する問題、慣れた後に生産性が伸びない）
- **根拠**: DORA 2025 の "AI acts as an amplifier" の知見
- **位置づけ**: 教材全体の前提。O3 以降はすべてこの主張の具体化である

### O3. タスクをエージェントに任せられる単位に分割し、必要なコンテキストを与えて指示できる【実践できる】

- **応答する課題**: 2（使ってみたが期待するアウトプットが得られない）
- **対応する capability**: Working in small batches / Documentation quality / AI-accessible internal data（部分採用）
- **根拠**: DORA はコンテキストの構成を **"context engineering"** と呼び、"giving teams AI tools that can access internal data directly amplifies the positive impact of AI adoption, serving as a statistically significant multiplier for individual effectiveness and code quality" と述べている。文書品質との関係も DORA が明示しており、"High-quality documentation is a primary driver of AI adoption"
- **扱う範囲**: AI-accessible internal data の実装3段階のうち**第1段階（手動のコンテキストエンジニアリング）のみ**。第2・第3段階は O6 で扱う

### O4. どこまで任せ、どこで人が確認するかを、リスクに応じて設計できる【実践できる】

- **応答する課題**: 3（使いどころの判断がつかない）
- **対応する capability**: Streamlining change approval（部分採用）
- **根拠**: 重量級の承認が変更失敗率を下げる証拠はなく、むしろバッチを大きくし遅くする。リスクに応じて承認の重さを変えることが推奨されている

### O5. AIの出力を安全に受け入れる仕組みを、自分の開発に組み込める【実践できる】

- **応答する課題**: 4（生成されたコードの品質を保てるか不安）
- **対応する capability**: Version control / Test automation / Continuous integration / Continuous delivery / Deployment automation / Pervasive security（部分採用）
- **根拠**: セキュリティテストの自動化について "code can be continuously tested at scale without requiring a manual review"。エージェントが大量のコードを出すとき人間のレビューはスケールしない
- **扱う範囲**: Continuous integration では trunk-based development の3閾値（アクティブブランチ3つ以下、1日1回以上 trunk にマージ、コードフリーズを設けない）を明示的に扱う

### O6. 効果が出ないとき、制約がどこにあるかを見立て、組織に働きかけられる【説明できる】

- **応答する課題**: 5・6
- **対応する capability**: Visibility of work in the value stream / Work in process limits / Loosely coupled teams / Clear and communicated AI stance / AI-accessible internal data / Platform engineering / User-centric focus
- **根拠**: WIP 制限は "expose problems in the system so they can be addressed" のための装置であり、"Without doing this, it's impossible to see the actual bottlenecks"
- **扱う範囲1**: Visibility of work in the value stream と Work in process limits は**セットで扱う**。両者は相互に補強する循環であり、一方向の手順として書かない
- **扱う範囲2**: AI-accessible internal data は実装の第2・第3段階（RAG / MCP による自動化、セキュリティ基盤を伴う運用）。第1段階は O3 で「実践できる」水準として扱う

## 扱わないこと

範囲が広がりすぎるのを防ぐため、次は扱わない。教材の冒頭で明示する。

| 扱わないこと | 理由 |
|---|---|
| 特定の言語・フレームワークの習得 | デモで使う題材の範囲を超えない |
| エージェント自体の開発（SDK・MCP 実装） | エージェントを使う側に徹する |
| 経営・投資判断の材料（ROI・製品比較・ツール選定） | 受講者は現場のエンジニアである |
| 組織の承認プロセスそのものの改定 | Streamlining change approval の部分採用で落とした部分 |
| InfoSec チームとの協働体制、承認済みライブラリの整備 | Pervasive security の部分採用で落とした部分 |
| LLM の仕組み・プロンプト工学の体系的な理論 | 実践に必要な範囲に限って扱う |
| SAST / DAST / 依存関係スキャンの製品比較 | ツール選定は扱わない範囲 |

## 教材の要件

1. **各章は、`audience.md` の「受講者が抱えている課題」のいずれかに応答するものでなければならない。**
2. **前提知識が「なし」の領域は、教材内で説明する。前提にしてはいけない。** 該当するのはコーディングエージェント、ユニットテストの作成、CI/CD パイプライン。

要件2は分量に直接効く。テスト自動化と CI/CD を前提にできないため、これらを教材内で扱う必要がある。

## 執筆時の規約

**DORA の記述と、私たちの論を書き分ける。** DORA が AI との関連を明示しているのは AI カテゴリの capability のみである。それ以外の capability が「AI 駆動開発で効く」という主張は私たちの論であり、DORA の記述ではない。

**推論による対応づけを追加する場合は、第2部に記録し、教材では出典として DORA を挙げない。** 現時点で推論による対応づけは存在しない。

**Human in the loop / on the loop、Loop Engineering は DORA の語彙ではない。** 教材に載せるなら別途出典が必要。DORA が使うのは **"context engineering"** である（AI-accessible internal data）。

**同一 capability を複数の目標に置く場合は、水準の違いを明示する。** 現在該当するのは AI-accessible internal data のみ（O3 で実践、O6 で説明）。

## 章立て

全9章。軸は**「人手の検査に頼らない」**である。1〜2章で前提を作り、3章でエージェントに渡すものを整え、4章で人が確認する場所を絞り、5〜7章で人手の検査を自動化された検査に置き換え、8〜9章で残る制約を扱う。

5〜7章は「検査を作る（5章）→ 検査を自動で回す（6章）→ 届ける（7章）」と積み上げ、継続的デリバリーを到達点として7章で回収する。

### 時間配分

**教材の全9章 660分は、研修の2日間（講義正味 約600分）には収まらない。**

**研修で講義するのは1〜7章（555分）とする。8〜9章は45分で要点だけを扱い、詳細は教材に委ねる。** 教材の分量は削らない。

```

       ├─→ 3章 スモールバッチとコンテキスト
       │     └─→ 4章 人による確認
       │           └─→ 5章 バージョン管理とテスト自動化
       │                 ├─→ 6章 継続的インテグレーション

       │                 └───────────↑（7章は5章と6章の両方を前提にする）

```

**5〜7章の系列と8〜9章の系列は、2章から独立に分岐する。** 8〜9章は5〜7章を前提にしない。

## 章ごとの詳細

### 1章 コーディングエージェントを使った開発

- **応答する課題**: 1（エージェントを使った開発のイメージが湧いていない）
- **到達目標**: エージェントを使った開発の流れを、教材を見ながら自分の環境で再現できる
- **中心となる主張**: エージェントを使った開発は、チャットにコードを書かせることとは別の作業である
- **扱わないこと**: ツールの製品比較・選定、エージェント自体の実装
- **節構成**
  1. チャットとエージェントは何が違うか
  2. デモ: エージェントに小さな変更を任せる
  3. 自分の環境で再現する
  4. エージェントがうまくいかないところ
- **執筆時に守ること**
  - 2節と3節はデモ手順を含む。`/verify-demo` の対象になる
  - 2節のデモは、プロジェクト固有の指示がリポジトリに置かれた状態で行う。指示が短く済む理由はここでは説明せず、3章に持ち越すと予告する
  - ツール固有の記述（Claude Code の `CLAUDE.md`）は囲みに入れ、出典と確認日を書く

### 2章 コーディングだけ速くしても全体は速くならない

- **応答する課題**: 5・6（使い始めてから遭遇する問題、慣れた後に生産性が伸びない）
- **到達目標**: AIにコードを書かせるだけでは生産性が上がらないことを、根拠を挙げて説明できる
- **中心となる主張**: AIは既存のシステムを増幅する。制約がコーディング速度の外にあるなら、コーディングを速くしても全体は変わらない
- **扱わないこと**: ROI の試算、AI導入の投資判断
- **節構成**
  1. 速くなったのはどこか（1章のデモを素材に、変更が生まれてから届くまでを分解する）
  2. AIは増幅器である
  3. この教材の残りが何をするか（3章以降の地図）
- **執筆時に守ること**
  - 1節で**検査が律速になること**を明示する。5〜7章（検査の自動化）の動機をここで置く
  - 3節の地図では、速度の制約がどこにあるかと、3〜4章・5〜7章がそれぞれどれに応えるかを対応づける

### 3章 スモールバッチとコンテキスト

- **応答する課題**: 2（使ってみたが期待するアウトプットが得られない）
- **到達目標**: タスクをエージェントに任せられる単位に分割し、必要なコンテキストを与えて指示できる
- **中心となる主張**: エージェントの出力の質は、渡したコンテキストとタスクの大きさで決まる
- **扱わないこと**: プロンプト工学の体系的な理論、RAG / MCP によるコンテキスト供給の自動化（9章で扱う）
- **節構成**
  1. 大きなタスクは失敗する
  2. タスクを分割する
  3. コンテキストを渡す
  4. 文書の品質が出力を決める
  5. デモ: 同じ依頼を、文書が整ったリポジトリと整っていないリポジトリで比べる
- **執筆時に守ること**
  - AI-accessible internal data の第1段階（手動のコンテキストエンジニアリング）に限る
  - **5節の比較軸を「プロンプトの違い」にしない。** 差の原因がシステム側にあることを実演で示す
  - 3節で、**コンテキストをリポジトリに常駐させること**（毎回渡さない）と、**繰り返す手順を再利用できる形にすること**を扱う。ツール固有の記述（Claude Code の `CLAUDE.md` と skills）は囲みに入れ、出典と確認日を書く。1章2節のデモで見せた状態を、ここで原理として回収する
  - skills の分量が節1つ分に育つ場合は6節に分ける

### 4章 人による確認

- **応答する課題**: 3（使いどころの判断がつかない）
- **到達目標**: どこまで任せ、どこで人が確認するかを、リスクに応じて設計できる
- **中心となる主張**: 人の確認を増やしても変更失敗率は減らず、開発が遅くなるだけである
- **扱わないこと**: 組織の承認プロセスそのものの改定
- **節構成**
  1. 重い承認は失敗率を下げず、変更を遅くする
  2. リスクで確認の重さを変える
  3. 自分の作業ループのどこに確認を置くか
- **執筆時に守ること**
  - 「変更失敗率」は `glossary.md` に登録し、初出で定義する
  - 3節は5章への橋になる。人の確認を減らした分をどこで埋めるかを問いとして残す

### 5章 バージョン管理とテスト自動化

- **応答する課題**: 4（生成されたコードの品質を保てるか不安）
- **到達目標**: 変更を戻せる状態と、自動で品質を確かめる仕組みを、自分の開発に組み込める
- **中心となる主張**: エージェントの出力を安全に受け入れる土台は、いつでも戻せることと、自動で確かめられることである
- **扱わないこと**: 特定のテストフレームワークの網羅的な使い方
- **節構成**
  1. いつでも戻せることが前提になる
  2. 自動テストは何を保証するか
  3. テストを書く
  4. エージェントにテストを書かせるときの注意
  5. デモ: テストを土台にエージェントへ変更を任せる
- **執筆時に守ること**
  - 3節は前提知識「ユニットテストの作成: なし」を埋める。教材の要件2により省略できない

### 6章 継続的インテグレーション

- **応答する課題**: 4
- **到達目標**: 変更を1日1回以上統合し、自動で検証される状態を作れる
- **中心となる主張**: 統合と検査を自動で回さないかぎり、エージェントが出す変更の量に人手は追いつかない
- **扱わないこと**: CI 製品の比較・選定、SAST / DAST / 依存関係スキャンの製品比較、InfoSec チームとの協働体制、承認済みライブラリの整備
- **節構成**
  1. 統合を遅らせると何が起きるか
  2. 継続的インテグレーションの3つの閾値
  3. パイプラインを組む
  4. セキュリティの検査をパイプラインに入れる
  5. 壊れたら止める
- **執筆時に守ること**
  - 2節で trunk-based development の3閾値（アクティブブランチ3つ以下、1日1回以上 trunk にマージ、コードフリーズを設けない）を明示的に扱う
  - 3節は前提知識「CI/CD パイプライン: なし」を埋める
  - この章を継続的デリバリーへの入口として位置づける

### 7章 継続的デリバリー

- **応答する課題**: 4
- **到達目標**: 変更を届けるまでを自動化し、いつでも安全に届けられる状態を保てる
- **中心となる主張**: 5〜7章で積み上げてきたものの到達点が継続的デリバリーである
- **扱わないこと**: デプロイツールの比較・選定
- **節構成**
  1. デプロイを自動化する
  2. いつでも届けられる状態とは何か（継続的デリバリーの回収）
  3. 4章の設計を更新する
- **執筆時に守ること**
  - 2節で、継続的デリバリーが5〜7章の総体であることを示す
  - 3節で4章に戻り、自動検査が増えた後に人の確認をどこへ置き直すかを扱う。軸「人手の検査に頼らない」がここで閉じる

### 8章 制約を探す

- **応答する課題**: 5・6
- **到達目標**: 効果が出ないとき、制約がどこにあるかを見立てられる
- **中心となる主張**: 制約は見えなければ直せない
- **扱わないこと**: 特定のプロジェクト管理ツールの使い方
- **節構成**
  1. 仕事の流れを見えるようにする
  2. 仕掛かりを制限すると問題が表に出る
  3. チームの構造が制約になるとき

# 第2部 判断の記録

同じ検討を繰り返さないために残す。**この部は執筆・レビューの判定基準ではない。**

## 「実践できる」をこう定義した理由

研修は講義中心で演習がなく、研修中に実務で実行できる水準には到達しない。`audience.md` で「研修後の自習」を教材の直接の読者と定義したことに対応させ、**教材を見ながら実務で実行できる**ことを到達点とした。

## 学習目標の順序

**O2 は O1 の後に置く。** エージェントを使った開発がどんなものか分からないうちは、「それだけでは速くならない」も実感できない。一度手を動かしてから聞くほうが納得しやすい。

**O1 の課題を解くのは説明ではなく再現である。** 研修中はデモを見て、研修後に自分で再現する（`audience.md`「受講者が教材を読む状況」）という設計にそのまま対応させた。

## 章立ての軸と順序

軸「人手の検査に頼らない」は、Pervasive security の "without requiring a manual review" と、Streamlining change approval の「重量級の人手承認は変更失敗率を下げない」が同じ方向を指していることによる。どちらも人手の検査を、自動化された検査とリスクベースの判断に置き換える。この軸により、4章（人の確認を減らす）と5〜7章（自動検査に置き換える）が一続きになる。

順序の制約は次のとおり満たしている。

- **Pervasive security は Test automation の後**（6章 ← 5章）。受講者はユニットテストの作成を前提にできないため
- **Continuous integration は Version control と Test automation の後**（6章 ← 5章）。CI は両者を組み合わせた実践である
- **O2 は O1 の後**（2章 ← 1章）
- **8章は2章を前提にする。** 8〜9章は2章の主張（制約はコーディング速度の外にある）を組織スケールで具体化したものであり、5〜7章を前提にしない

## 時間配分をこう決めた理由

2日間の講義正味は約600分（1日6時間から休憩・導入・まとめを除く）。教材の全9章 660分は収まらない。

**教材を削るのではなく、研修で講義する範囲を絞った。** これが成立するのは、`audience.md` で研修後の自習を教材の直接の読者と定義し、「実践できる」を教材を手元に置いて実務で実行できることと定義しているためである。研修で全章に触れることは、目標の達成条件ではない。

**圧縮する対象を8〜9章にしたのは2つの理由による。** この2章が O6（説明できる）であり、実践水準の章より自習で届きやすいこと。そして5〜7章を前提にしないため、外しても前後がつながること。

5〜7章が重い点は、各章のアウトライン設計時に再検討する。

## 章ごとの配置の判断

**2章に速度の問題提起を置いた。** 5〜7章で検査を自動化する動機は安全性だけではない。AIのコーディング速度を活かすには検査も速くする必要がある。この論はもともと4章の根拠（重い承認はバッチを大きくし遅くする）に含まれていたが、書き落としていた。新しい章は作らず、2章1節と4章の主張に戻した。

**3章が「プロンプトのコツ」として読まれないようにした。** そう読まれると、2章の主張（制約はコーディング速度の外にある）と逆向きになる。これは見送った学習目標「自分の進め方を振り返って改善できる」を却下したのと同じ構造である。歯止めとしてデモの比較軸を変えた。プロンプトの違いではなく、文書が整ったリポジトリと整っていないリポジトリを比べる。

**Pervasive security を6章に置いた。** 論拠が "code can be continuously tested at scale without requiring a manual review" であり、パイプラインに検査を積む話だからである。順序制約（Test automation の後）も満たす。当初は7章に置いていたが、7章が「到達点の回収」と「部品の追加」を同時に担うことになるため移した。

**継続的デリバリーを7章の到達点にした。** DORA は "continuous integration is only one element of implementing continuous delivery" と述べており、CD の foundational drivers には Version control / Test automation / Continuous integration / Pervasive security / Deployment automation が含まれる。CD は6章の上位概念ではなく5〜7章全体の上位概念である。包含を理由に6章と7章を統合すると、同じ理由が5章にも当てはまり、5〜7章が1章に戻ってしまう。

**`CLAUDE.md` と skills の置き場を3章3節にした。** 原則としての名前は「コンテキストをリポジトリに常駐させる」と「繰り返す手順を再利用できる形にする」である。実行イメージは1章2節のデモで先に見せ、原理は3章で回収する。

**最初に執筆するのは1章2節。** コマンド5個とサブエージェント5個は、まだ一度も動いていない未検証の仕組みである（`retrospectives/phase-0-1.md` P3）。大きな章から着手すると、仕組みの問題と内容の問題が同時に噴出して切り分けられない。

## 章タイトルの付け方

スタイルは統一していない。形を内容に従わせている。

1. **名前があるものは、名前で呼ぶ。** 確立した用語がある対象は、説明的に言い換えず用語をそのままタイトルにする（3・5・6・7章）。目次が索引として機能する
2. **対象に名前がなく、読者の行為そのものが主題の章は動詞にする**（8・9章）
3. **主張を込めるタイトルは1つだけにする。** 2章以外は中立的な名前にし、目次を見たとき2章だけが文として浮き上がるようにする

個別に立てる固有の中身が残らないため、採用済みの capability の中で扱う。

### 部分採用の歯止め

capability の一部だけを採用する場合、次の2条件を満たすこと。無制限に許すと「DORA に基づく」と謳いながら中身が独自解釈になる。

1. その部分だけで一つの観察可能な行動として成立すること
2. 元の capability の主眼から外れていないこと

## 見送った学習目標

### 自分の進め方を振り返って改善できる

インタビューで「受講後の姿」として挙がった項目だが、学習目標には立てない（2026-08-31 決定）。

**主たる理由は中心的主張と向きが逆になることである。** 教材の主張は「制約はコーディング速度ではなく、その周りのシステムにある」。一方この目標は、うまくいかない原因を**自分の使い方**に向ける。受講者が半年後に「思ったより速くならない」と感じたとき、この目標は個人技の改善へ、O2 と O6 はシステムの改善へ誘導する。並べて置くと、受講者はより馴染みのある前者に流れる。

副次的な理由として、DORA の裏付けがない。候補の `Learning culture`（研修予算、心理的安全性、知識共有の場）と `Team experimentation`（チーム外の許可なくアイデアを試せる権限）は、いずれも組織・チームスケールであり、個人の振り返りを裏付けない。

失われるものの受け皿は次のとおり。

| 失われるもの | 受け皿 |
|---|---|
| 課題6への応答 | O6 が対応する。しかも「制約はどこか」という正しい向きで |
| 受講後も学び続けること | `audience.md` の「教材は後で戻ってくる場所として読まれる」で担保。目標に立てなくても、教材の書き方の制約として機能する |
| 受講者の期待「判断基準を持ち帰る」 | O3・O4 が直接対応する |
