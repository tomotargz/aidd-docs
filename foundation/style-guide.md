# スタイルガイド

**この文書に書くのは「どう書くか」だけである。** 誰に向けて書くかは `audience.md`、何を教えるかは `curriculum.md` に書く。

執筆時とレビュー時の両方で参照する。`style-reviewer` と `writing-reviewer` はこの文書を判定基準にする。

ここに書かれたルールは、振り返り（`/retro`）で得られた知見を反映して更新していく。**ルールを追加した理由はコミットメッセージに書く。この文書には書かない。** 過去の判断は `git log -- foundation/style-guide.md` で辿る。

---

## 1. パラグラフライティング

段落は教材の最小単位である。段落単位で意味が完結していれば、受講者は拾い読みでも論旨を追える。

1. **1段落1トピック**。ひとつの段落で主張することはひとつに限る。
2. **段落の第1文は要約文（トピックセンテンス）にする**。第1文だけを拾い読みしても、節の論旨が通ること。
3. 第2文以降は、第1文の**根拠・詳細・具体例**のいずれかに限る。新しい主張を持ち込まない。
4. 段落の長さは**3〜6文、200〜400字**を目安にする。超える場合はトピックが複数混ざっている疑いがある。
5. 段落の並び順は、節の主張から演繹される順序にする。時系列や思いつき順に並べない。
6. **見出しの直下には、その見出しの主張を1文で置く**。この1文がスライド化時のリード文になる。

## 2. テクニカルライティング

1. **一文一義**。ひとつの文で述べることはひとつ。80字を超えたら分割を検討する。
2. **主語と述語を近づける**。間に長い修飾節を挟まない。
3. **修飾語は被修飾語の直前に置く**。係り受けが二通りに読めないこと。
4. **曖昧語を使わない**。「など」「適切に」「基本的に」「かなり」「しっかり」は、具体的な語に置き換えるか削除する。**例外**: 具体化に多くの記述を要し、そのために読者の負担が増える場合は、頻度や程度の語を使ってよい。出典のある数値が手元にあるときは、例外を使わず数値を書く。
5. **指示語は、直前の名詞が一意に定まるときだけ使う**。「これ」「それ」が段落をまたぐ場合は名詞を繰り返す。**段落の第1文では指示語を使わない。** 拾い読みしたときに指す先が失われる。
6. **二重否定を使わない**。「〜しないわけではない」は肯定形に直す。
7. **能動態を基本にする**。動作の主体が誰かを明示する。
8. **並列は文法的に揃える**。箇条書きの各項目は同じ品詞・同じ構造にする。
9. **数値と条件は具体的に書く**。「多くの場合」ではなく「3件中2件で」と書けるなら書く。書けない場合の扱いは4の例外による。
10. **同じ語を1文のなかで2回使わない**。「担い手が移ると、仕事も移る」のように動詞が重なる文は、一方を言い換えるか文を分ける。
11. **動作の主語には、動作を行う人か物を置く**。「担い手」「移動」のような抽象名詞を主語にしない。

## 3. 表記

| 項目 | ルール |
|---|---|
| 文体 | ですます調 |
| 英数字 | 半角 |
| 和欧文間のスペース | 入れない（例: `Claude Codeを使う`）。ただし囲みのラベルと出典行では、区切りとして半角スペースを入れる（例: `**Claude Code v2.0 時点**`、`（2026-08-22 確認）`） |
| 括弧 | 和文中は全角（）、コード・コマンド内は半角 |
| 句読点 | 「、」「。」 |
| 感嘆符・疑問符 | 原則使わない |
| 数字と単位 | 半角、間にスペースを入れない（例: `3件`、`80字`） |
| 箇条書きの記号 | **番号付き（`1.`）を既定にする。** 記号（`-`）を使うのは、順序も件数も項目の対応づけも関係しない列挙だけである |
| 箇条書きの文末 | 文になる項目は「。」で終える。体言止めの項目は句点なし。**1つのリスト内で混在させない** |
| 用語 | `glossary.md` の表記に従う。同一概念に複数の呼び方をしない |
| 強調 | **本文では強調記法を使わない。** 傍点・下線・色も使わない。囲み（`> [!NOTE]`）のラベルにのみ `**太字**` を使う |
| コード・コマンド・ファイル名 | バッククォートで囲む |

**件数を本文で述べているリストは、必ず番号付きにする。**

**強調したいことは、段落の第1文に置く。** パラグラフライティングの1と2がすでにその手段になっている。

この表は教材の原稿に適用する。`foundation/` の設計文書には適用しない。

## 4. 見出しと文書構造

スライド化（Marp / Slidev）を見据えた制約を、執筆時点から守る。変換時の手戻りを防ぐため。

| 見出し | 役割 | 制約 |
|---|---|---|
| H1 | セクションのタイトル | ファイルに1つだけ |
| H2 | **スライド1枚分の主題** | 直下に主張文を1文置く。配下の本文は600字以内を目安にする |
| H3 | H2 内の論点 | 見出しの深さは H3 まで。H4 以下は使わない |

## 3.1 英文の引用

一次情報を英文で引用するときは、原文と訳を引用ブロックの中にセットで置く。

- **訳は本文に書かない。** 引用ブロックの中に置く。本文は教材自身の主張だけにする
- 訳には `訳:` のラベルを付ける。原典の日本語ではなく、教材側の訳であることを示す
- 原文と訳は交互に並べる。原文を続けてから訳を続けると、対応が順番だけで決まる
- 一部だけを訳して残りを放置しない
- 本文で英語の原語に触れるときは、半角ダブルクォートで囲み、前後にスペースを入れない

```markdown
> "原文をそのまま"
> 訳: 原文の日本語。
> "2つ目の原文"
> 訳: 2つ目の日本語。
> 出典: https://example.com/page （2026-08-22 確認）
```

## 4.1 図

工程の並びや流れを示すときは図を使う。表は、項目ごとに複数の属性を並べるときに使う。

- 図はコードブロックに書く。言語の指定はしない
- 矢印は `→` を使う。縦につなぐときは `↓`、特定の箇所を指すときは `↑`
- 図に書くのは並びと関係だけにする。各項目の説明は本文に書く
- 順序を主張しない列挙は、図ではなく箇条書きにする
- 罫線素片（`┌` `─` `┐`）は使わない。スライド化で崩れる

```
コードを変える → レビュー → テスト → 統合 → リリース
     ↑
  ここだけが速くなった
```

## 5. ツール固有の記述

原則は寿命が長く、ツールの仕様は短い。両者を混ぜると、教材全体が短命になる。

- ツール固有の操作・設定・挙動は、**必ず囲みの中に書く**。

```markdown
> [!NOTE]
> **Claude Code v2.0 時点** — サブエージェントは `.claude/agents/` に配置します。
> 出典: https://example.com/docs （2026-08-22 確認）
```

- 囲みの外は、ツールが変わっても成立する原則の記述に限る。
- ツール固有の記述には**必ず出典 URL と確認日を書く**。同じ内容を `sources/references.md` にも記録する。
- 囲みを含むファイルは、frontmatter に `tool_version` を記載する。
- **節全体がツール固有になる場合は、冒頭に一括宣言の囲みを置く。** 個々の記述を囲みに入れる代わりに、「この節に出てくるコマンドとキー操作は、すべて〈ツール名〉のものです」と冒頭で宣言し、節末に出典と確認日の囲みを置く。この形を使えるのは、節の到達目標がツールの操作そのものである場合に限る。

## 6. frontmatter

教材の各 Markdown ファイルの冒頭に置く。

```yaml
---
title: AIに任せる境界
chapter: 1
section: 2
status: draft        # draft | reviewed | fixed
updated: 2026-08-22
sources:             # 参照した一次情報（sources/references.md の ID）
  - REF-003
tool_version:        # ツール固有記述がある場合のみ
  claude_code: "2.0"
demo_source: demos/ch01-02-shop  # デモの題材を置いたディレクトリ。デモ手順を含む場合のみ
demo_verified:       # デモ手順を含む場合のみ。/verify-demo で実行確認した日
  date: 2026-08-22
  os: macOS 15
---
```

| status | 意味 |
|---|---|
| `draft` | 執筆済み、レビュー未実施 |
| `reviewed` | `/review-doc` 実施済み、指摘が未反映 |
| `fixed` | Critical / High の指摘をすべて反映済み。マージ可能 |

## 6.1 デモ手順の書き方

教材は研修後に受講者が一人で読み、デモで見た操作を再現する（`audience.md`「教材の使われ方」）。

- **講師の口頭説明を前提にした省略をしない。** 読むだけで再現できる粒度で書く。
- 手順が前の手順の結果に依存する場合、その依存を明示する。
- 環境（OS、シェル、ツールのバージョン）に依存する手順は、依存を明記する。
- 出力例を載せる場合は、実際の出力をそのまま引用する。整形や省略をする場合はその旨を書く。
- **デモの題材は `demos/<章-節>-<スラッグ>/` に置き、そのファイルを正とする。** 原稿のコードブロックは引用として書き、frontmatter の `demo_source` に置き場所を書く。
- **デモ手順を含むファイルは `/verify-demo` の検証を通すまでマージしない。**

## 7. 禁止事項

- 出典のないツール固有の断定
- 受講者を主語にした決めつけ（「あなたはこう感じるはずです」）
- 根拠を示さない優劣の主張（「〜のほうが優れています」）
- 未定義の専門用語の初出使用（`glossary.md` に登録し、初出時に定義する）
