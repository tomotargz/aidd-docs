# はじめに

## この教材の目的

コーディングエージェントでコードを書く時間を短くしても、開発全体が速くなるとは限りません。

コードを書く時間は確かに短くなります。しかし設計、レビュー、テスト、リリースのどこかが詰まっていれば、そこで止まります。詰まっている場所に流し込む量を増やせば、その場所はかえって混みます。レビュー待ちの列は長くなり、テストがなければ誤りが見つかるのは後の工程になり、そこからの戻りが増えます。

この構図を、DORAは2025年の研究で述べています。DORAは、ソフトウェア開発の実践と成果の関係を継続的に調査している研究プログラムです。

> "AI acts as an amplifier, but the greatest returns come from focusing on the underlying sociotechnical systems."
> 出典: https://dora.dev/research/?view=detail （2026-09-08 確認）

AIは既存のやり方を増幅する、と述べています。増幅されるのは速さだけではありません。そして最大の効果は、その下にある仕組み、つまり人とツールと手順の組み合わせに手を入れたときに得られる、と続きます。

この教材が教えるのは、AIが効く状態を作るエンジニアリングです。AIを速く使う技術ではありません。その状態を作ることが、DORAの言う「下にある仕組み」に手を入れることにあたります。

## 読み終えてできるようになること

この教材を読み終えると、次の6つができるようになります。

1. コーディングエージェントを使った開発を、自分の手元で再現できる。
2. AIにコードを書かせるだけでは生産性が上がらない理由を、根拠を挙げて説明できる。
3. タスクをエージェントに任せられる単位に分け、必要な情報を渡して指示できる。
4. どこまで任せ、どこで人が確認するかを、リスクに応じて設計できる。
5. AIの出力を安全に受け入れる仕組みを、自分の開発に組み込める。
6. 効果が出ないとき、制約がどこにあるかを見立て、組織に働きかけられる。

1つ目は1章で、2つ目は2章で扱います。3つ目から5つ目までが3章から7章、6つ目が8章と9章です。

> [!IMPORTANT]
> この教材は、AIの使い方を覚えれば明日から速くなるという即効性を提供しません。コーディングエージェントの操作は1章で扱いますが、2章から9章は、エージェントが出す変更を安全に速く届けること、そして残っている詰まりを見つけて変えることに使います。
> 納得できない主張があれば、その場で判断せず、最後まで読んでから判断してください。

## 想定読者

この教材は、コードを書く現場のエンジニアに向けて書いています。

前提とする知識は次のとおりです。「あり」とした知識は、説明せずに使います。

| 領域 | 前提 |
|---|---|
| プログラミングの実務経験 | あり（3年以上を想定） |
| Git / GitHubでのブランチとプルリクエスト | あり |
| ターミナルでのコマンドライン操作 | あり |
| チャット型の生成AIの利用 | あり |
| コーディングエージェント | なし |
| ユニットテストを書く習慣 | なし |
| CI/CDパイプラインの構築・運用 | なし |

表の下3行が「なし」であることが、教材の構成を決めています。コーディングエージェントは、チャット型の生成AIとの違いから説明します。ユニットテストとCI/CDは、書いたことがない人が読める粒度で扱います。

コーディングエージェントとチャット型の生成AIは、どちらもコードを書きます。違いは、ファイルを読んでコマンドを実行するところまで自分で行うかどうかです。この違いは1章1節で扱います。

想定していない読者もいます。導入の可否を判断する立場の人と、コードを書かない職種の人です。費用対効果の試算や製品比較は扱いません。

## 扱わないこと

範囲が広がりすぎるのを防ぐため、次の7つは扱いません。

| 扱わないこと | 理由 |
|---|---|
| 特定の言語・フレームワークの習得 | 扱う範囲をデモの題材にとどめるため |
| コーディングエージェント自体の開発（他システムと接続するための実装） | エージェントを使う側に徹するため |
| 経営・投資判断の材料（費用対効果の試算、製品比較、ツール選定） | 読者が現場のエンジニアであるため |
| 組織の承認プロセスを改定する手順 | 手順そのものは一人では動かせないため |
| セキュリティ部門との協働体制、承認済みライブラリの整備 | 同じく、体制づくりは一人では動かせないため |
| AIモデルの仕組み、プロンプト工学の体系的な理論 | 実践に必要な範囲に限るため |
| セキュリティ検査ツール（コードを解析するもの、動かして試すもの）の製品比較 | ツール選定が範囲外であるため |

扱わないのは進め方であり、必要性の説明材料は扱います。承認プロセスやセキュリティ体制について、なぜ変えるべきかを説明できる水準までは9章で扱います。改定を進める手順は扱いません。

## この教材の読み方

この教材は、研修が終わったあとに一人で読まれることを想定して書いています。

この教材に触れる形は、研修中と研修後で変わります。研修中は、スライドを見ながら講師の説明を聞き、操作は講師のデモとして見ます。自分で手を動かすのは研修後で、この教材を読みながらデモで見た操作を自分の環境で再現します。

そのため、質問できる相手がいない状態で読めることを、書き方の基準にしています。講師の口頭説明を前提にした省略はしません。

手を動かすために必要なものは、コーディングエージェントの導入と、題材にする小さなリポジトリの2つです。導入の手順と題材の中身は1章3節にあります。1章3節の所要時間は20分です。

囲みの読み方を先にお伝えします。実際の囲みは次の形で現れます。

> [!NOTE]
> **〈ツール名〉 v〈バージョン〉 時点** — このツールの設定ファイルは、プロジェクトの直下に置きます。
> 出典: 〈URL〉 （〈確認日〉 確認）

バージョンと出典と確認日が入った囲みは、特定のツールについての記述です。ツールは変わります。囲みの中身は、時間が経てば古くなります。

囲みの外に書いてあることは、ツールが変わっても成り立つ話です。原則とツールの仕様を分けているのは、ツールの仕様のほうが先に古くなるからです。

デモと例で使うコーディングエージェントは、1章1節で1つに決めます。理由と、ほかのエージェントとの関係もそこで述べます。

## 目次

本編は全9章で、3つのまとまりに分かれます。

| 章 | タイトル | 前提とする章 | 時間（目安） |
|---|---|---|---|
| 1 | コーディングエージェントを使った開発 | — | 60分 |
| 2 | コーディングだけ速くしても全体は速くならない | 1 | 45分 |
| 3 | スモールバッチとコンテキスト | 1・2 | 90分 |
| 4 | 人による確認 | 3 | 60分 |
| 5 | バージョン管理とテスト自動化 | 4 | 120分 |
| 6 | 継続的インテグレーション | 5 | 110分 |
| 7 | 継続的デリバリー | 5・6 | 70分 |
| 8 | 制約を探す | 2 | 60分 |
| 9 | 組織に働きかける | 8 | 45分 |

時間は講義したときの目安です。研修で講義するのは1章から7章までで、8章と9章は要点だけを扱い、詳細はこの教材に委ねます。

3つのまとまりは次のとおりです。1章から4章は、エージェントに何をどこまで任せ、それがどこまで効くのかを扱います。5章から7章は、任せた結果を安全に届ける方法を扱います。8章と9章は、自分のチームで詰まっている場所を見つけ、変える方法を扱います。

前から順に読むことを想定していますが、5章から7章は飛ばせます。8章と9章は2章だけを前提とするためです。
