# 速くなったのはどこか

## はじめに

1章でデモしたように、エージェントはコーディングを高速化しますが、それは開発プロセスの一部にすぎません。

この節では、開発プロセスに含まれる工程のうち、エージェントを使うことで速くなったもの、変わらなかったものを見ていきます。

## デモが終わった時点で何ができたか

1章のデモでは、エージェントが`price.py`を1行書き換えて、テストが通るようになりました。

```
$ git diff
diff --git a/price.py b/price.py
index 331cb4a..d4242f3 100644
--- a/price.py
+++ b/price.py
@@ -1,2 +1,2 @@
 def format_price(yen):
-    return f"¥{yen}"
+    return f"¥{yen:,}"
```

この時点では開発が完了したとは言えません。変更は自分の作業ディレクトリにあるだけです。コミットとプッシュをしていないので、ほかの開発者が変更を見ることはできません。リリースもしていないので、ユーザーにこの変更は届いていません。

## エージェントが速くしたのは開発プロセスの一部

コーディングを始めてから開発が完了するまでには、以下のような工程が含まれます。

- コーディング
- レビュー
- テスト
- 統合
- リリース

デモで見せたような基本的な使い方でエージェントが高速化できるのは、コーディングです。

自分の現場に当てはめてみてください。コードを変えてからリリースするまでに、いくつ工程がありますか。そのうち、エージェントが高速化できそうなもの、できなそうなものはどれですか。

## 検査がボトルネックになる

多くの場合、エージェントを使った開発では、検査がボトルネックになります。検査とは、変更が正しいか確かめる工程です。先に挙げた工程のうち、レビューとテストが検査にあたります。

エージェントにより変更の量が増えると、検査の負荷が高まります。DORAは2026年の記事で次のように述べています。

> "higher AI adoption is associated with an increase in both software delivery throughput and software delivery instability."
> "the time saved during initial code or content generation is often re-allocated to verification overhead and prompting overhead"
> 出典: https://dora.dev/insights/balancing-ai-tensions/ （2026-09-09 確認）

検査が追いつかなければ、エージェントを使ってもリリースまでの時間は短くなりません。検査を人によるレビューや手動テストに頼っているならば、変更の量が増えると待ち行列が長くなります。新しい変更を速く作ることができても、長い待ち行列に阻まれて、リリースは速くなりません。

エージェント利用の恩恵にあやかるためには、検査を効率化する必要があります。レビューについては4章、テストについては5章から7章で扱います。

現場によっては検査以外の工程にボトルネックが生じることもあります。リリースが月に1回の現場なら、そちらが先に詰まっているかもしれません。自分の現場でどこがボトルネックになっているかを見立てる方法は、8章で扱います。

## この節で確かめたこと

エージェントを使うことで速くなったのは、開発プロセスの一部工程だけでした。残りの工程は基本的なエージェントの使い方では速くなりません。

変更を出す量が増えるほど、検査の列は長くなります。なぜこうなるのか、そして増幅されるのが速さだけではないことを、次の節で扱います。
