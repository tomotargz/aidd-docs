# 速くなったのはどこか

## はじめに

1章3節では「速くなったのはコードを変える工程だけ」という結論だけを置きました。この節では、その根拠を工程に分解して確かめます。

変更が生まれてから使われるまでの工程を並べ、どれが速くなり、どれが変わらなかったかを見ます。この節は読むだけで進み、手を動かす必要はありません。

## デモが終わった時点で何ができたか

1章のデモが終わった時点で、変更はまだ誰にも届いていません。

できたのは、`price.py`の1行が書き換わり、テストが通る状態になったことです。1章2節では、その結果を`git diff`で確認しました。次の引用は、1章2節に載せた2026-09-07の実行記録です。

```
$ git diff
diff --git a/price.py b/price.py
index 331cb4a..d4242f3 100644
--- a/price.py
+++ b/price.py
@@ -1,2 +1,2 @@
 def format_price(yen):
-    return f"¥{yen}"
+    return f"¥{yen:,}"
```

エージェントが作業を終えた時点でも、変更は自分の作業ディレクトリにあるだけです。コミットもしていません。ほかの誰も、この変更を見ていません。

## 変更が届くまでの工程

書いた変更が使われるまでには、コードを変えたあとに4つの工程が並びます。

```
コードを変える → レビュー → テスト → 統合 → リリース
```

4つの工程は、それぞれ別の目的を持ちます。

1. レビューでは、ほかの人が変更を読み、受け入れるかを決めます。
2. テストでは、変更がほかの部分を壊していないかを確かめます。
3. 統合では、ほかの人が同じ期間に書いた変更と合わせます。
4. リリースでは、使える状態にして届けます。

並び方は現場によって変わります。テストをレビューより先に走らせることも、両方を同時に行うこともあります。ここで見たいのは順序ではなく、コードを変えたあとに残る工程の数です。

## エージェントが短くした工程

エージェントが短くしたのは、コードを変える工程だけです。

```
コードを変える → レビュー → テスト → 統合 → リリース
     ↑
  ここだけが速くなった
```

残りの4つの工程が短くならない理由は、工程ごとに違います。

1. レビューは人が読む工程です。読む作業の一部をエージェントに任せることはできますが、受け入れるかを最終的に決めるのは人です。どこまで任せるかは4章で扱います。
2. テストは、1章のデモでもエージェントが実行しました。実行できたのは、`test_price.py`が先に用意されていたからです。テストコードがなければ、この工程は動きません。
3. 統合は、ほかの人の変更が出そろうまで始められません。
4. リリースは、届ける手順を人が動かす工程です。

1章のデモではコミットもしていないため、レビュー、統合、リリースの3つには触れていません。

デモは1行の変更でした。最小のケースでも、コードを変えたあとに4つの工程が残ります。変更が大きくなれば、残る工程はさらに重くなります。

自分の現場に当てはめてみてください。コードを変えてから使われるまでに、いくつ工程がありますか。そのうち、エージェントが短くしたのはどれですか。レビュー待ちがあり、リリースが週に1回なら、5つ以上に分かれるはずです。

## 検査がボトルネックになる

変更を出す量が増えると、検査がボトルネックになりえます。

検査とは、変更が正しいかを確かめる工程です。図に並べた5つの工程のうち、レビューとテストが検査にあたります。

AIの利用が進むと、届けられる変更の量が増えます。そして、コードを書く時間が短くなったぶんは、確かめる時間に移ります。DORAは2026年の記事で次のように述べています。

> "higher AI adoption is associated with an increase in both software delivery throughput and software delivery instability."
> "the time saved during initial code or content generation is often re-allocated to verification overhead and prompting overhead"
> 出典: https://dora.dev/insights/balancing-ai-tensions/ （2026-09-09 確認）

出す量が増えても、レビューする人の数と1件あたりの所要時間は変わりません。レビュー待ちの列は長くなります。

テストコードがなければ、誤りは統合やリリースのあとまで見つかりません。見つかる時点が遅いほど、原因を探して直す範囲は広がります。

コードを変える工程を速くしても、検査が追いつかなければ、変更が届くまでの時間は短くなりません。

どの工程がボトルネックかは現場によって変わります。リリースが月に1回の現場なら、そちらが先に詰まっているかもしれません。自分の現場でどこが詰まっているかを見立てる方法は、8章で扱います。

テストを人手に頼らずに回す方法は、5章から7章で扱います。レビューをどこに残すかは4章で扱います。

## この節で確かめたこと

速くなったのは、変更が届くまでの工程のうち1つだけでした。

残りの4つの工程は、エージェントを入れても短くなりません。テストだけは、テストコードが先に用意されていれば動きます。

変更を出す量が増えるほど、検査の列は長くなります。なぜこうなるのか、そして増幅されるのが速さだけではないことを、次の節で扱います。
