# 速くなったのはどこか

## はじめに

この節では、1章で速くなった工程を特定します。

特定するために、変更が生まれてから使われるまでの工程を並べます。並べたうえで、どの工程が速くなり、どの工程が変わらなかったかを見ます。

この節は読むだけで進みます。手を動かす必要はありません。

## デモが終わった時点で何ができたか

1章のデモが終わった時点で、変更はまだ誰にも届いていません。

できたのは、`price.py`の1行が書き換わり、テストが通る状態になったことです。1章2節では、その結果を`git diff`で確認しました。

```
$ git diff
diff --git a/price.py b/price.py
index 331cb4a..d4242f3 100644
--- a/price.py
+++ b/price.py
@@ -1,2 +1,2 @@
 def format_price(yen):
-    return f"¥{yen}"
+    return f"¥{yen:,}"
```

この時点で変更は自分の作業ディレクトリにあるだけです。コミットもしていません。ほかの誰も、この変更を見ていません。

## 変更が届くまでの工程

書いた変更が使われるまでには、コードを変えたあとに4つの工程が並びます。

```
コードを変える → レビュー → テスト → 統合 → リリース
```

レビューでは、ほかの人が変更を読み、受け入れるかを決めます。テストでは、変更がほかの部分を壊していないかを確かめます。統合では、ほかの人が同じ期間に書いた変更と合わせます。リリースでは、使える状態にして届けます。

並び方は現場によって変わります。テストをレビューより先に走らせることも、両方を同時に行うこともあります。ここで見たいのは順序ではなく、コードを変えたあとに残る工程の数です。

## エージェントが短くした工程

エージェントが短くしたのは、図の左端にある1つだけです。

```
コードを変える → レビュー → テスト → 統合 → リリース
     ↑
  ここだけが速くなった
```

レビューは人が読む工程なので、エージェントを使っても読む速さは変わりません。テストは、テストコードがなければ実行できません。統合とリリースは、それぞれ別の作業です。1章のデモには、これらのどれも出てきませんでした。

自分の現場に当てはめてみてください。コードを変えてから使われるまでに、いくつ工程がありますか。そのうち、エージェントが短くしたのはどれですか。

## 検査が律速になる

変更を出す速さが上がると、全体の速さは検査で決まります。

検査とは、変更が正しいかを確かめる工程です。図に並べた5つのうち、レビューとテストがこれにあたります。

エージェントを使うと、1人が1日に出せる変更が増えます。出す量が増えても、読む人の数と読む速さは変わりません。レビュー待ちの列は長くなります。テストコードがなければ、誤りが見つかるのは統合やリリースのあとになり、そこから戻る距離が長くなります。

コードを変える工程を速くしても、検査が追いつかなければ、変更が届くまでの時間は短くなりません。この状態を、検査がボトルネックになっているといいます。

検査を人手に頼らずに回す方法は、5章から7章で扱います。この節では、そこが詰まりうることを確認できれば十分です。

## この節で確かめたこと

速くなったのは、変更が届くまでの工程のうち1つだけでした。

残りの4つは、1章のデモには出てきませんでした。そして変更を出す速さが上がるほど、検査の列は長くなります。

なぜ1つの工程を速くしても全体が変わらないのかを、次の節で扱います。
