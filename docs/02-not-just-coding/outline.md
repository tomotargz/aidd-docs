# 2章 コーディングだけ速くしても全体は速くならない アウトライン

## 章の到達目標

AIにコードを書かせるだけでは生産性が上がらないことを、根拠を挙げて説明できる。

## 章の主張

AIは既存のシステムを増幅する。制約がコーディング速度の外にあるなら、コーディングを速くしても全体は変わらない。

## 前提として既知のこと

- `audience.md` の前提知識（実務経験、Git / GitHub、ターミナル、チャット型の生成AI）
- 0章: 教材の目的、DORA の引用（1回だけ提示済み）、扱わないこと
- 1章: コーディングエージェントの定義、ループ（情報収集・変更・動作確認）、人が関わる3か所、1章2節のデモ（テストを1件通す変更）、1章3節で自分の環境で再現した経験

**ユニットテストと CI/CD は前提「なし」である。** 工程の名前として触れるが、構築や運用には踏み込まない。

## セクション構成

配分は章全体で45分。3節それぞれ15分を目安にする。

### 1節 速くなったのはどこか

- **主張**: 1章で速くなったのは、コードを変える工程だけである。変更が生まれてから届くまでには、ほかの工程が並んでいる。
- **根拠**
  - 1章2節のデモを素材にする。エージェントが短くしたのは「コードを変える」工程である。テストは実行されたが、テストコードが先に用意されていたためである
  - その変更が実際に使われるまでには、レビュー、テスト、統合、リリースが並ぶ。受講者が実務で通している工程である（前提「あり」）。**工程の並びは図で示す**（`style-guide.md`「4.1 図」）
  - エージェントは変更を速く出すが、確かめる側は速くならない。**検査（レビューとテスト）がボトルネックになりうる**。どの工程が詰まっているかは現場によって変わり、見立て方は8章で扱う
  - 1人が1日に出せる変更が増えるほど、検査の列は長くなる
- **理解の変化**: 「エージェントで開発が速くなった」→ 速くなったのは1工程だけで、その先が詰まると分かる
- **扱わないこと**: 計測の手法、ボトルネックの探し方（8章）、検査を自動化する方法（5〜7章）
- **ツール固有の記述**: なし。1章のデモを素材にするが、ツールの挙動には触れない

### 2節 AIは増幅器である

- **主張**: AIは既存のやり方を増幅する。増幅されるのは速さだけではない。
- **根拠**
  - DORA 2025 の "AI acts as an amplifier, but the greatest returns come from focusing on the underlying sociotechnical systems."（REF-002）。0章では宣言として置いた。ここで根拠として展開する
  - 増幅の中身: 土台が整っていれば効果が大きく、整っていなければ問題も大きくなる
  - 1節で見た検査の列は、増幅の具体例である。出す量が増えれば、確かめる量も増える
  - したがって、制約がコーディング速度の外にあるなら、コーディングを速くしても全体は変わらない
- **理解の変化**: AIを入れれば速くなる → 何がどれだけ増幅されるかは土台で決まると分かる
- **扱わないこと**: 費用対効果の試算、AI導入の投資判断
- **ツール固有の記述**: なし

### 3節 この教材の残りが何をするか

- **主張**: 制約がどこにあるかによって打ち手が変わり、3章から9章はそれぞれ別の制約に応えている。
- **根拠**
  - 1節で分解した工程のどこに制約があるかで、打つ手が変わる
  - 渡すものが足りず、任せる単位が大きい → 3章
  - 人の確認が詰まっている → 4章
  - 検査が人手で追いつかない → 5章・6章・7章
  - 制約がどこにあるか分からない、一人では動かせない → 8章・9章
  - 0章の目次は章の並びを示した。ここでは制約と章を対応づける
  - **章の中心となる主張の後半「制約がコーディング速度の外にあるなら、コーディングを速くしても全体は変わらない」は、この節で述べる。**2節では述べないと決めた（2節のレビューでの判断）
- **理解の変化**: 章がなぜこの順に並ぶか分からない → 自分の現場の詰まりと章が対応づく
- **扱わないこと**: 各章の中身。ここでは対応づけだけを示す
- **ツール固有の記述**: なし
