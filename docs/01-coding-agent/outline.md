# 1章 コーディングエージェントを使った開発 アウトライン

## 章の到達目標

コーディングエージェントを使った開発の流れを、教材を見ながら自分の環境で再現できる。

## 章の主張

コーディングエージェントを使った開発は、チャットにコードを書かせることとは別の作業である。

## 前提として既知のこと

この章は教材の最初の章であり、前の章で説明済みの概念はない。`audience.md` の前提知識だけを土台にする。

- プログラミングの実務経験（3年以上）
- Git / GitHub でブランチを切り、PR を出してレビューを受ける流れ
- ターミナルでのコマンドライン操作
- チャット型の生成AI（ChatGPT 等）の日常的な利用

**コーディングエージェントは未経験である。** 「エージェント」という語も、この章で初めて定義する。

**インストールと認証は、この章の範囲外とする。** 公式ドキュメントを読めば完遂できるため、教材では済んでいる状態から始める。

## セクション構成

配分は章全体で60分。1節15分、2節25分、3節20分を目安にする。

### 1節 チャットとエージェントは何が違うか

- **主張**: エージェントは、指示を受けたあと自分でファイルを読み、変更し、コマンドを実行して結果を確かめる。チャットでは人が担っていたこのループを、エージェントが自分で回す。
- **根拠**
  - チャット型生成AIを使うとき、必要な情報を集めて貼り付け、返ってきたコードを反映し、動かして確かめるのは人である（受講者がすでにやっていること）
  - エージェントは "reads your codebase, edits files, runs commands" と説明される（REF-016）
  - 違いは出力の賢さではなく、**ループを誰が回すか**にある
  - その結果、人の仕事は「書くこと」から「任せる範囲を決め、結果を受け入れるか判断すること」へ移る
- **理解の変化**: 「賢いチャット」だと思っている → 作業ループの担い手が変わる道具だと分かる
- **扱わないこと**: モデルの仕組み、プロンプトの書き方、ツールの製品比較
- **ツール固有の記述**: あり。Claude Code の定義（REF-016）を囲みに入れる

### 2節 デモ: エージェントに小さな変更を任せる

- **主張**: 人の指示で始まり、「コンテキストを集める → 動く → 結果を確かめる」を完了まで繰り返し、完了で人に戻る。人はこの入口と出口だけでなく、途中のどの時点でも割り込める。
- **根拠**
  - 全体の形は「人の指示 → ループ（3局面の繰り返し） → 完了」である。公式ドキュメントの図は `Your prompt` から始まり、`Gather context` → `Take action` → `Verify results` を `repeat` で回し、`Done` で終わる。図の外に `You: interrupt, steer, or add context` が置かれている（REF-020）
  - 3局面の名前は公式ドキュメントの記述に合わせる。"it works through three phases: **gather context**, **take action**, and **verify results**"（REF-020）
  - 局面は分かれて進むのではなく混ざる。"These phases blend together."（REF-020）
  - 何回まわるかはタスクによる。質問ならコンテキスト収集だけで終わり、バグ修正は3局面を繰り返す（REF-020）
  - 人もループの一部である。"You can interrupt at any point to steer Claude in a different direction, provide additional context, or ask it to try a different approach."（REF-020）
  - 小さな変更をひとつ任せた実際の記録を、出力の実物で示す。各局面でエージェントが何をしたかを、実行されたコマンドとファイルの差分で対応づける
  - このデモはプロジェクト固有の指示がリポジトリに置かれた状態で行う。指示が短く済む理由はここでは説明せず、3章に持ち越すと予告する
- **理解の変化**: 手順の説明を読んでも像が結ばない → 一巡の形（入口・繰り返し・出口・割り込み）を、実物と対応づけて知る
- **扱わないこと**: 大きなタスク、複数ファイルにまたがる設計変更（3章で扱う）。指示の組み立て方（3章）。エージェントが失敗する条件（3章）
- **ツール固有の記述**: あり。3局面の記述（REF-020）、実行コマンドと出力、`CLAUDE.md`（REF-017）を囲みに入れる。**`/verify-demo` の対象**

> [!IMPORTANT]
> 3局面は Claude Code の公式ドキュメントの記述である。**他のコーディングエージェントも同じ動きをするとは書かない。**
> 一般化するには別の出典が必要になる（`curriculum.md`「執筆時の規約」）。

### 3節 自分の環境で再現する

- **主張**: 2節と同じ一巡は、教材を見ながら自分のリポジトリで再現できる。
- **根拠**
  - インストールと認証が済んでいることを前提とする。手順は公式ドキュメントを案内するに留める（REF-019）
  - 起動と動作確認（`claude --version`、プロジェクトディレクトリでの起動）
  - 2節と同じ変更を、自分のリポジトリで一度実行する
  - 割り込み、変更の取り消し、実行を許可するかの判断（REF-020）。2節で「割り込める」と述べたことを、操作として渡す
  - 環境による差（OS、シェル）が出る箇所を明示する
- **理解の変化**: デモを見ただけ → 自分の手元で同じことができ、途中で止めて戻せる
- **扱わないこと**: インストールと認証の詳細、ターミナル以外の surface、権限のチーム運用、どこに人の確認を置くかの設計（4章）
- **ツール固有の記述**: 節全体がツール固有になる。REF-019・REF-020 を出典とし、確認日とバージョンを frontmatter の `tool_version` に書く。**`/verify-demo` の対象**

## 自己点検

### 各節の主張を並べたとき、章の主張が導かれるか

1節「ループを回すのがエージェントに移る」→ 2節「その一巡は3局面をたどり、人は割り込める」→ 3節「自分でも再現でき、止めて戻せる」。

**導かれる。** 章の主張「チャットにコードを書かせることとは別の作業である」は、1節（ループの担い手）が正面から支え、2節と3節が実物と操作で裏づける。

### 前提知識だけで1節から読み進められるか

**読み進められる。** 1節はチャット型生成AIの利用経験を出発点にしており、これは前提「あり」である。2節以降はターミナル操作と Git の知識を使うが、いずれも前提「あり」である。

ユニットテストと CI/CD には触れない。どちらも前提「なし」であり、この章では必要にならない。

### 到達目標に寄与しない節が混ざっていないか

**混ざっていない。** 1節が全体像、2節が手本、3節が再現そのものを担う。

### 節の数と分量は適切か

**2節が最も重い。** 3局面の説明とデモの実物が同居する。分量が節1つに収まらない場合は、3局面の説明を1節の末尾へ移す。

節を増やす必要はない。3節構成で60分に収まる。
