# タスクを分割する

## はじめに

この節では、エージェントに任せる仕事をどこで区切るかを扱います。

区切る基準は、人がその結果を確かめて受け入れられるかどうかです。エージェントはコードを書く速さを上げますが、書かれたものを人が確かめる速さは上げません。

## 生成が安くなると、一度に頼む量が増える

コードを書く費用が下がると、一度に頼む量は増えます。

エージェントには、短い指示で大量のコードを書かせられます。1つずつ頼んで待つより、まとめて頼むほうが早く終わるように見えます。頼む側の手間は、頼む量が10倍になっても変わりません。

DORAは、仕事を十分に小さく割らないことを落とし穴の1つに挙げ、これがAIツールで起きやすいと書いています。

> "This pitfall is common with AI tools, which are often optimized for generating large, complete features."
> 訳: この落とし穴はAIツールでよく起きる。AIツールは、大きく完結した機能を生成するように最適化されていることが多い。
> "Avoid the temptation to generate massive pull requests"
> 訳: 巨大なプルリクエストを生成したくなる誘惑を避けること。
> 出典: https://dora.dev/capabilities/working-in-small-batches/ （2026-09-13 確認）

## 確かめる速さは変わらない

書く速さが上がっても、その結果を人が確かめる速さは上がりません。

レビューも、テスト結果の解釈も、人が読んで判断する作業です。エージェントは、この部分を肩代わりしません。

DORAは、機械が生成したコードのほうが読む負荷が高くなりうると書いています。

> "the cognitive load required to review a small chunk of machine-generated code may be higher per line than reviewing human-written code"
> 訳: 機械が生成したコードは、小さな塊をレビューするのに必要な認知負荷が、人が書いたコードより1行あたり高くなりうる。
> 出典: https://dora.dev/capabilities/working-in-small-batches/ （2026-09-13 確認）

自分で書いたコードには、書いた過程の記憶が残ります。どこで何を判断したかを思い出せます。エージェントが書いたコードには、それがありません。読んで、意図を推測し、正しいかを確かめる作業になります。

ここで釣り合いが崩れます。頼む量は増やせますが、確かめられる量は増えません。確かめきれない量が返ってきたとき、受け入れるかどうかの判断ができません。判断できないものは、確かめずに受け入れるか、捨てて自分で書き直すかのどちらかになります。

## 区切りは、受け入れを決める地点に置く

仕事の区切りは、人が受け入れるかどうかを決める地点に置きます。

ここでいう区切りとは、1つの変更に着手してから、それを確かめて他の人に渡せる状態にするまでのまとまりです。エージェントへの依頼1回とは別のものです。1回の依頼で1つの区切りが終わることもあれば、依頼を何回か重ねて1つの区切りになることもあります。

```
依頼 → 依頼 → 依頼 → 人が受け入れを決める
                      ↑
                  ここで区切りが終わる
```

依頼の回数には基準を置きません。基準を置くのは区切りの側です。仕事を小さく区切って進めることを、DORAはスモールバッチと呼びます。

区切りが大きいときと、1回の依頼が大きいときでは、起きることが違います。区切りが大きいと、人が確かめきれません。1回の依頼が大きいと、エージェントが自分で決める箇所が増えます。判断が1つ外れると、その先の作業は外れた前提の上に積み上がります。

## 区切りの大きさを決める基準

区切りの大きさは、確かめられるかどうかで決めます。

DORAは、仕事を割る単位が満たすべき条件として、テストできること、監視できること、利用者が期待するとおりに動くと検証できることを挙げています。

> "Each batch of work can be tested, monitored, and verified as working in the way users expect."
> 訳: それぞれの仕事の塊が、テストでき、監視でき、利用者が期待するとおりに動いていると検証できること。
> 出典: https://dora.dev/capabilities/working-in-small-batches/ （2026-09-13 確認）

時間の目安もあります。

> "Any batch of code that takes longer than a week to complete and check is too big."
> 訳: 完了して確認するまでに1週間を超えるコードの塊は、大きすぎる。
> 出典: https://dora.dev/capabilities/working-in-small-batches/ （2026-09-13 確認）

この1週間は、区切りに対する目安です。エージェントへの1回の依頼を測るものではありません。依頼は数分で終わります。

## 小さく分けても、まとめて出せば元に戻る

小さく分けた仕事をまとめ直して流すと、分けた効果は消えます。

DORAは、これをもう1つの落とし穴として挙げています。

> "Working in small batches but then regrouping the batches before sending them downstream for testing or release."
> 訳: 仕事を小さく分けたのに、テストやリリースのために下流へ送る前に、その塊をまとめ直してしまうこと。
> "Regrouping work in this way delays the feedback on whether the changes have defects"
> 訳: このようにまとめ直すと、変更に欠陥があるかどうかのフィードバックが遅れる。
> 出典: https://dora.dev/capabilities/working-in-small-batches/ （2026-09-13 確認）

エージェントを使うと、この形になりやすくなります。依頼を小刻みに出して作業を進めても、最後に1つのプルリクエストにまとめれば、確かめる人が向き合う量は分ける前と同じです。区切りの大きさは、確かめる人に渡る時点で決まります。

## いまの区切りの大きさを測る

自分がいまどれくらいの大きさで区切っているかは、1つの問いで測れます。

> "What proportion of features can you complete in one week or less?"
> 訳: 1週間以内に完了できる機能は、どれくらいの割合か。
> 出典: https://dora.dev/capabilities/working-in-small-batches/ （2026-09-13 確認）

完了とは、コードを書き終えることではありません。確かめて、他の人に渡せる状態にするところまでです。この問いに答えられない機能があるなら、そこが区切り直す対象になります。

## まとめ

この節では、エージェントに任せる仕事をどこで区切るかを扱いました。

1. コードを書く費用が下がると、一度に頼む量は増える。
2. 確かめる速さは上がらない。機械が生成したコードは、1行あたりの負荷が高くなりうる。
3. 区切りは、人が受け入れを決める地点に置く。依頼の回数には基準を置かない。
4. 区切りの大きさは、確かめられるかどうかで決める。1週間は区切りに対する目安である。
5. 小さく分けても、まとめて出せば元に戻る。
