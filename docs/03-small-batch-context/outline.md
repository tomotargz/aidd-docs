# 3章 スモールバッチとコンテキスト アウトライン

## 章の到達目標

タスクをエージェントに任せられる単位に分割し、必要なコンテキストを与えて指示できる。

## 章の主張

エージェントの出力の質は、渡したコンテキストとタスクの大きさで決まる。

## 前提として既知のこと

- `audience.md` の前提知識
- 0章: 教材の目的、扱わないこと、囲みの読み方
- 1章: コーディングエージェントの定義、ループ（情報収集・変更・動作確認）、人が関わる3か所、1章2節のデモ（`demo-shop`、`CLAUDE.md` を置いた状態）、権限モードと巻き戻し
- 2章: 工程、ボトルネック、スループット、不安定さ、増幅器、土台、検査。**3章が「エージェントに渡すもの」のボトルネックに応えること**

**1章2節の末尾で「1行で済む変更だから任せられたのではないか」という疑問を残している。** 1節でこれに答える。

## 主張が変わったときの扱い

**執筆中に一次情報を読み直して新しい発見があれば、節の主張は変えてよい。** 変えたときは、原稿だけでなくこの文書も直す。直さないと `logic-reviewer` が「アウトラインとの不一致」を指摘し、どちらが正しいかを毎回説明することになる。

## セクション構成

配分は章全体で90分。1節15分、2節20分、3節20分、4節15分、5節20分を目安にする。

### 1節 大きなタスクは失敗する

- **主張**: 一度に任せる範囲が大きいほど、返ってくるものが期待から外れる。
- **根拠**
  - 1章2節のデモは1行の変更だった。そこで残した疑問に、ここで答える
  - 任せる範囲が大きいほど、エージェントが自分で決める箇所が増える。判断が1つ外れると、その先がすべて外れる
  - 人が確かめる単位も大きくなる。差分が大きいほど、受け入れるかの判断が重くなる（1章で見た出口）
  - DORA の Working in small batches。**個別ページの出典登録が必要**（現在は REF-001 のカタログのみ）
- **理解の変化**: 指示の書き方が悪いと思っている（`audience.md` 課題2）→ 任せる範囲の大きさが効いていると分かる
- **扱わないこと**: 分割の手順（2節）、プロンプトの書き方
- **ツール固有の記述**: なし

### 2節 タスクを分割する

- **主張**: エージェントに任せる単位は、人が結果を確かめられる大きさにする。
- **根拠**
  - 分割の基準を「エージェントが失敗しない大きさ」ではなく「人が確かめられる大きさ」に置く。確かめられなければ、受け入れる判断ができない
  - 1つの変更が1つの目的に対応していること
  - 1章2節のデモ（テストを1件通す）が、その最小の形である
  - 大きな仕事を分けるときは、動くところまでを先に作り、次に広げる
  - DORA の Working in small batches
- **理解の変化**: どこで切ればよいか分からない → 確かめられる大きさが基準だと分かる
- **扱わないこと**: 見積もりやタスク管理の手法、チームでの分担
- **ツール固有の記述**: なし

### 3節 コンテキストを渡す

- **主張**: 毎回同じことを説明しているなら、それはリポジトリに置く。
- **根拠**
  - 1章2節のデモで、指示は1文だった。テストの実行方法も規約も `CLAUDE.md` にあった。**その仕組みを、ここで原理として回収する**
  - 渡すものは2種類ある。毎回変わるもの（この変更で何をしたいか）と、変わらないもの（テストの実行方法、規約、プロジェクトの構造）
  - 変わらないものはリポジトリに常駐させる。毎回渡さない
  - 繰り返す手順は、再利用できる形にする
  - DORA はこれを context engineering と呼ぶ（REF-014）
- **理解の変化**: 毎回同じ説明をしている → 常駐させられるものと、その置き場所が分かる
- **扱わないこと**: RAG / MCP によるコンテキスト供給の自動化（9章）
- **ツール固有の記述**: あり。`CLAUDE.md`（REF-017）と skills（REF-018）を囲みに入れる

### 4節 文書の品質が出力を決める

- **主張**: エージェントに渡せる情報の品質が、出てくるものの品質を決める。
- **根拠**
  - "High-quality documentation is a primary driver of AI adoption."（REF-013・REF-014）
  - 内部データに直接アクセスできることが、個人の生産性とコードの品質の倍率として働く（REF-014）
  - 2章で「土台が結果を決める」と述べた。文書の品質はその土台の一部である
  - 文書の品質は、明確さ・見つけやすさ・信頼性などで測る（REF-013 の8指標）
  - **古い文書は、ないより悪い。** エージェントはそれを前提として使う
- **理解の変化**: 文書は人のために書くもの → エージェントの入力でもあると分かる
- **扱わないこと**: 文書の書き方の一般論、文書管理ツールの選定
- **ツール固有の記述**: なし

### 5節 デモ: 同じ依頼を、文書が整ったリポジトリと整っていないリポジトリで比べる

- **主張**: 同じ指示でも、リポジトリの状態が違えば結果が違う。
- **根拠**
  - 2つのリポジトリを用意する。コードは同じで、`CLAUDE.md` とテストの有無だけが違う
  - 同じ1文の指示を両方に与え、出力を並べる
  - **プロンプトが同一であることを明示する。比較軸を「プロンプトの違い」にしない**（`curriculum.md`「執筆時に守ること」）
  - 差の原因がリポジトリの側にあることを、実行の記録で示す
  - 題材は `demos/ch03-05-*/` に置く。**`/verify-demo` の対象**
- **理解の変化**: 差は指示の書き方で決まると思っている → リポジトリの状態で決まると分かる
- **扱わないこと**: プロンプトの比較、複数のエージェントの比較
- **ツール固有の記述**: 節全体がツール固有になる。`style-guide.md`「5. ツール固有の記述」の一括宣言の形を使う
