## Keep

**起案の前に論点をディスカッションで潰す。** PR #1 は初版を出してからレビューで7回直した。PR #3 は起案前に3つの論点を議論し、コミット1本で済んだ。同じ規模の設計作業で手戻りが7対0になった。

**判断の前に一次情報にあたる。** 5回の判断が覆った。いずれも記憶や推測で進めていたら誤った内容が教材に入っていた。特に `Documentation quality` は、私が「私たちの推論」と判定したものが実は DORA の記述だった。

**判断の理由を文書に残す。** 採用しなかった capability の理由、部分採用の歯止め、見送った学習目標の根拠を記録した。同じ検討を繰り返さずに済む。

## Problem

### P1. 応答と差分の分量が多く、レビューが負担になった

**原因**: 応答の長さに制約を設けていなかった。判断の根拠、選択肢、波及論点をすべて一度に提示していた。丁寧さと読みやすさを取り違えていた。

### P2. Phase 0 のテンプレートが文書の責務を混ぜていた

**原因**: `audience.md` のテンプレートに「受講後の姿」「想定しない読者」を含め、後者は読者ではなくトピックを書かせる構造になっていた。PR #1 の手戻り7件のうち5件がこれに起因する。テンプレートを作った時点で、各文書が何を書く場所かを定義していなかった。

### P3. 仕組みが一度も動いていない

**原因**: Phase 0 でコマンド5個とサブエージェント5個を作ったが、教材の原稿がないため実行できない。**未検証の仕組みが1,000行以上ある。** 初めて動かす章で問題が噴出する可能性が高い。

### P4. マージ後のバックログ更新の担当が未定義

**原因**: `CLAUDE.md` に「マージ時: チェックを付け、In Progress から外す」と書いたが、マージするのは人、バックログを更新するのは AI で、どちらがいつ行うかを決めていなかった。実際に2回とも1タスク遅れて反映された。
